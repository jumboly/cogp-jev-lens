# COGP 読み取りパイプライン（リーダー調達・LOD 選択・Worker 構成）
labels: design, frontend, cogp

## なぜ検討が必要か
表示範囲の POI を COGP から取る部分は Lens 以前の土台で、リーダーの取り込み方・LOD の選び方・スレッド構成で
転送量・件数・応答時間が決まる。公式 `cogp-js` は npm 未公開なので調達方法も決める必要がある。

## 現在わかっていること
- `cogp-js`（パッケージ名 `cogp` v1.0.0、MIT）は monorepo の一部で npm 未公開、`dist` も未コミット。ソース 7 ファイル・約 32 KB、依存は `hyparquet` + `hyparquet-compressors` のみ
- API: `CogpReader.open(url)` → `selectLevel(targetResolution)` → `readRows({ maxLevel, bbox, columns, maxRows, maxGeometryBytes })`。Range 合体・64 MiB Range キャッシュ・PageIndex 絞り込み・WKB 遅延デコードを内蔵
- 公式デモは Vite + MapLibre + Web Worker（`cogp-worker.ts`）。メインスレッドは bbox と解像度を送り、Worker が GeoJSON を返す
- 東京駅周辺 z14: L12 で約 4,300 件 / 13 MiB、L13 で約 8,800 件（`tags` 込み。転送量の 9 割が `tags`）

## 決定（2026-09-22）
- **リーダーは `v1.0.0` タグ固定で vendor 取り込み**（`src/vendor/cogp/` に src 7 ファイル + LICENSE）。更新はタグ指定の取り込みスクリプトで行う。submodule（postinstall で tsc が必要）と自前実装（PageIndex / Range 合体の再実装）は不採用
- 公式デモの Worker 構成は踏襲するが、コードは本プロジェクトの要件（タグ抽出・許可リスト・Lens 反映）に合わせて書き起こす
- **LOD 選択は「経度の度/px × 0.999」を `selectLevel` に渡す**。COGP の換算近似（1 度 = 111,320 m）と MapLibre の度/px の 0.0005% のずれで整数ズームが境界のすぐ下に落ちる問題を余裕で吸収し、全緯度で安定して L = z − 1 になる。開発パネルに **手動 ±1 の調整**を残し、件数差が Lens の見え方に与える影響をその場で比較できるようにする

- **Lens 適用前は全 POI を同じ小さな点で表示する**（色・大きさ一律の「無地の地図」）。許可リスト外の 1%（`office=yes` 等）も点として残し、Lens では常に中立。Popup で名前とタグを見せる。種別ごとの初期配色は Lens の色と意味が二重になるため不採用
- **読み取り上限は `maxRows: 20000` で開始**。z14 の都心（約 8,800 件）では余裕、z13 以下では上限に当たる見込みなので「表示範囲の一部しか読めていない」ことを画面に出す。低ズーム時の Lens 無効化（#10）と合わせて後で調整 → **2026-09-22 に 30000 へ引き上げ**（下記「上限を 30,000 件に引き上げた」）

## 訂正（2026-09-22、実装時の実測）
当初は「緯度補正した度/px」と決めたが、実ファイルを測って **緯度補正を外した**。

- COGP のレベル解像度は `360 / (1024 · 2^L)` のちょうど **0.9999954 倍**（L0〜L16 で一定）。MapLibre の度/px は `360 / (512 · 2^z)` なので、両者は L = z − 1 で一致し、0.0005% だけ足りずに境界を割る。これを吸収するのは **×0.999 の余裕**であって緯度補正ではない
- 緯度補正なしで、緯度 0 度から 70 度まで L = z − 1 になることを確認した。補正を入れると緯度 60 度以上でだけ L = z に振れ、1 段細かいレベルを余分に読む
- Web メルカトルでは経度の度/px はズームだけで決まるため、補正なしの方が画面上の点の密度が緯度によらず一定になる。公式デモも経度の度/px をそのまま渡している

## 上限 20,000 件が効く範囲（2026-09-22、1280×800 の画面・東京駅中心）

「上限で切った件数」しか出ないと読めている割合が分からないため、上限に当たったときだけ
**bbox 列だけを読み直して実件数を数える**（転送量の 9 割は `tags` なので、列を絞れば安い）。
実測では 0.2〜0.5 秒で返る。

| ズーム | レベル | 読んだ件数 | 実件数 | 読めた割合 |
| --- | --- | --- | --- | --- |
| z12 | L11 | 19,744 | — | 全部 |
| z11 | L10 | 20,000 | 23,900 | 84% |
| z10 | L9 | 20,000 | 26,404 | 76% |
| z9 | L8 | 20,000 | 20,208 | 99% |
| z8 | L7 | 14,813 | — | 全部 |

- 上限が効くのは **z9〜z11 の 3 段だけ**で、そこでも 76〜99% は読めている。LOD が粗くなる速さが
  表示範囲の広がる速さを上回るため、ズームを下げ続けても件数は増えず z8 以下でまた減る
- 下書きの想定（z13 以下で上限に当たる）より狭い範囲だった。低ズームの Lens 無効化（#10、z13 未満）は
  上限とは別の理由（空間間引きで代表性がない）で判断する必要がある
- 数える側にも上限（2,000,000 件）を置く。実測では届いていない

## 上限で切られる POI はどれか（2026-09-22、要注意）

リーダーは候補 row group を**先頭（粗い）から順に**流し、bbox に入る行を数えて `maxRows` で止める。
したがって切られるのは常に**末尾＝そのとき読む最細レベル**で、粗いレベルは必ず全部読める。
問題は、**レベル内の row group が空間順に並んでいるため、切り口が空間的に偏る**こと。

z10・東京駅中心・1280×800 で実測（実件数 26,404 / 読めた 20,000 / 切られた 6,404）。

| レベル | 読めた | 切られた |
| --- | --- | --- |
| L1〜L8 | 9,187 | 0 |
| L9（最細） | 10,813 | 6,404 |

切られた 6,404 件はすべて L9 で、かつ経度 139.328〜139.618（表示範囲の**西 1/3**）に収まっていた。

| 経度帯 | 読めた | 切られた | 欠落率 |
| --- | --- | --- | --- |
| 139.328〜139.474 | 2,764 | 2,414 | 47% |
| 139.474〜139.621 | 2,116 | 3,990 | 65% |
| 139.621〜139.767 | 6,550 | 0 | 0% |
| 139.767〜139.914 | 3,804 | 0 | 0% |
| 139.914〜140.060 | 2,784 | 0 | 0% |
| 140.060〜140.207 | 1,982 | 0 | 0% |

つまり「全体が一様に薄くなる」のではなく、**画面の一部だけが穴になる**。しかも画面上はそれと分からない。

- Lens で「この辺りは子供向けが少ない」と読ませると、西側では**単に読めていないだけ**を
  「少ない」と誤読させる。低ズームの Lens 無効化（#10）は空間間引きの代表性だけでなく、
  この切り口の偏りからも正当化される
- 影響するのは上限が効く z9〜z11 の 3 段のみ。#10 の閾値 z13 を維持するなら Lens には影響しないが、
  Lens 適用前の素の点表示では z9〜z11 で穴が見えることになる
## 上限を 30,000 件に引き上げた（決定、2026-09-22）

検討した案は 3 つ。

| | 案 | 判断 |
| --- | --- | --- |
| a | `maxRows` を実件数が収まる水準まで上げる | **採用** |
| b | 上限を超えると分かったら 1 段粗いレベルに落として一様に薄くする | 不採用。穴は消えるが解像度が下がり、ズームと見え方の対応が崩れる |
| c | 穴になっている範囲を画面に出す | 不採用。正直だが読み手に負担を寄せる。a で穴自体をなくせる |

`maxRows: 20000` → **`30000`**。引き上げ後は z9〜z11 でも上限に当たらず、実件数がそのまま出る。

| ズーム | レベル | 件数 | 読み取り | 転送 |
| --- | --- | --- | --- | --- |
| z14 | L13 | 5,845 | 約 1.2 秒 | キャッシュ済み |
| z12 | L11 | 19,744 | 約 0.9 秒 | 4.8 MiB |
| z11 | L10 | 23,900 | 約 1.3 秒 | 4.3 MiB |
| z10 | L9 | 26,404 | 約 1.1 秒 | 4.7 MiB |
| z9 | L8 | 20,208 | 約 0.8 秒 | 1.6 MiB |

余裕の確認として主要都市の z9〜z11 も測った（1280×800）。最大は東京 z10 の 26,404 件で、
**30,000 には約 12% の余裕**がある。

| 都市 | z11 | z10 | z9 |
| --- | --- | --- | --- |
| 東京 | 23,900 | 26,404 | 20,208 |
| パリ | 22,428 | 18,375 | 12,737 |
| ロンドン | 19,685 | 17,613 | 16,853 |
| ベルリン | 19,540 | 16,341 | 14,561 |
| 大阪 | 16,606 | 15,671 | 12,817 |
| ニューヨーク | 12,916 | 13,242 | 11,892 |

- 読み取り時間は 0.6〜1.3 秒で、20,000 のときと体感差はない
- 上限に当たったときの実件数表示は安全網として残す。画面がもっと大きい場合や、
  未測定の高密度域では再び当たりうる
