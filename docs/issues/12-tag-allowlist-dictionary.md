# タグ許可リスト・正規化辞書の生成
labels: design, data

## なぜ検討が必要か
1 回しか出ないペアが 191 万ある一方、上位 1 万ペアで出現の 91% をカバーする。
ビューポート内の全ユニークペアを無条件に JEV に送ると、ロングテール（タイポ・独自値）に無駄な評価が出る。

## 現在わかっていること
- 全世界の `key=value` 頻度表はプロファイリングで生成済み（`top_pairs_overall.csv` ほか）
- 正規化の要点: `;` 分解（`cuisine` は 68k → 13k 種）、`lower()`/`trim()`（効果は小さい）、`shop=yes` 等の種別不明値
- 許可リストは (a) タイポ排除、(b) 正規化、(c) 表示用説明文（OSM wiki）の付与、(d) 事前計算キャッシュの鍵、を兼ねられる

## 未決事項
- 閾値（世界で ≥N 件）。1〜2 万ペア（91〜93%）が目安
- 許可リスト外のペアの扱い: 評価しない / 低優先で評価 / キーだけで評価
- 静的 JSON として配布するか、BFF 側で持つか
- OSM wiki の説明文を機械的に取れるか（Taginfo API）

## 結論（2026-09-22、一部）
- 許可リスト方式を採用。閾値は「世界で 100 回以上」または「日本域で 20 回以上」の二段基準（#2 の議論で決定、東京駅周辺の抽出結果を見て日本基準を追加）
- 未決: ブランドの表記ゆれを `brand:wikidata` で束ねるか
- 対象キーは `docs/tag-policy.md` の分類キー・細分キー + `brand`
- 生成は `scripts/build_allowlist.py`。説明文の付与は未決

## 配布形態の決定（2026-09-22）
- **絞った静的 JSON をブラウザに配る**。`data-dist/tag-allowlist.v1.slim.json`（121 KiB、gzip 39 KiB）を
  `build_allowlist.py` が本体と同時に出す。持たせるのは「キーの役割」と「通す key=value の集合」だけで、
  出現回数・国別集計は落とす（本体 648 KiB の 1/5）
- BFF 側で絞る案は不採用。フロントは軽くなるが、「評価対象 N 種」を画面に出すのに往復が要る。
  絞り込みは JEV を呼ぶ前の判断なので、呼ぶ側が持つ方が素直
- **正規化はフロントと生成スクリプトで同じ規則**にする（ずれると命中しない）。
  値を `;` で分割して trim し、role が `brand` のキー以外は小文字化する
- 同数ペアの並びが SQL で決まらず再生成のたびに差分が出ていたので、
  出現数の降順 → `key=value` の昇順で並びを固定した。2 回生成して一致を確認済み
