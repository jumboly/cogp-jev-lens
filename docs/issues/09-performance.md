# パフォーマンス測定
labels: performance

## なぜ検討が必要か
COGP の Range 取得、JEV のレイテンシ、集約、描画のどこが支配的かを測らないと改善の優先順位が付かない。

## 現在わかっていること
- COGP: 東京駅周辺 z14 で約 13 MiB・145 リクエスト・約 1 秒（`tags` 込み）。geometry のみなら 1.7 MiB
- JEV: 1 リクエストに複数質問を束ねられる。レイテンシは未計測
- ユニークタグ数は表示範囲の POI 数の 1/10 程度になる見込み（別プロジェクトの実測: 4,604 件 → 428 種別）



## Vercel AI Gateway の実測（2026-09-22、実験 01 全体）

| 項目 | 値 |
| --- | --- |
| リクエスト数 | 1.5K（成功 約 950、残りは 429 / 503 で再試行したもの） |
| 成功率 | **65.3%** |
| トークン | 約 10M（入力 約 9.5M） |
| 課金 | **$0.00**（`typesafe-ai/jev` の Cost 欄も $0） |
| Gateway 側 P50 Duration | 198 ms（クライアント実測は 40 問で約 550 ms） |
| 予算 | キー $5 / チーム $10 |

- Gateway 経由の JEV は現時点で **課金されていない**。コストの制約は金額ではなく **レート制限（成功率 65%）** にある
- 上流の混雑（429 "high demand"）と 503 が散発する。BFF には指数バックオフの再試行と、同時リクエスト数の制限が必須
- JEV: Gateway 側 P50 198 ms、クライアント実測 約 550 ms / 40 問。744 タグ × 3 プリミティブ = 57 リクエストを直列で流すと約 30 秒。並列化とキャッシュが要る

## 実測（2026-09-22、段階 9）

計測方法（未決事項の 1 つ目）は **画面に出す**ことにした。COGP の読み取りは `#status`、
集約とキャッシュ復元は `#perf`、JEV は Lens の進捗行に出る。別途プロファイラを回さずに、
操作しながらどこが遅いかを読めるようにしておく。

| 工程 | 時間 | 条件 |
| --- | --- | --- |
| COGP 読み取り（Range + WKB デコード + タグ正規化） | **0.9〜1.5 秒** | z14 / 5,845 件 / 1280×800 |
| キャッシュ復元（IndexedDB） | **8 ms** | 1,779 件 |
| 集約 + `setData`（メインスレッド占有） | **1〜4 ms** | 5,845 件 |
| JEV 評価（冷えた Lens） | **108〜200 秒** | 21 バッチ時代の実測。上流の状態で 1 桁変わる |
| JEV 評価（温かい Lens） | **0** | キャッシュ命中 |

## 結論（2026-09-22）

- **支配的なのは JEV（冷えているとき）。** 次に COGP の読み取り。集約と描画は無視できる
- したがって改善は **「JEV を呼ぶ回数を減らす」**に集中した。
  キャッシュ（#6）と、1 リクエストの重さを揃えたバッチ分割（#4 の改善案 1、21 本 → 16 本）を実装
- **所要時間の改善は数字で出せていない。** 段階 9 の作業中はずっと上流が不調で
  （503 が 5 割超、429 も混ざる）、16 本にした後の通し実測を完遂できなかった。
  減ったのはリクエスト本数と 1 本の重さで、そこは確定している
- **目標値**（未決事項の 2 つ目）:
  - **温かい Lens は 100 ms 以内**。実測は集約 4 ms + 復元 8 ms で達成している
  - **冷えた Lens には所要時間の目標を置かない。** 上流の状態で 1 桁変わるので目標にしても
    意味がない。代わりに「最初の結果が届くまで」を見る（実測 12 秒で 5,027 件に反映）
- 集約を `feature-state` ではなく GeoJSON 差し替えにした判断（#8）は妥当だった。
  5,845 件を毎回作り直しても 1〜4 ms で、評価が届くたびに塗り直しても詰まらない
- COGP の 0.9〜1.5 秒は転送量の 9 割が `tags` 列（#13）。Lens に必要なのは
  許可リストを通ったタグだけなので、**読む列を絞れば縮む見込みがある**（未着手）
