# MapLibre での AI Lens 可視化
labels: design, frontend

## なぜ検討が必要か
「検索」ではなく「Lens」であることを、表示の変化で伝えたい。POI の集合は変えず、見え方だけを変える。

## 現在わかっていること
- 仮案: サイズ → Score、透明度 → relevance、色 → Choice、Popup → JEV 詳細
- 取得と評価を分離し、POI をまず通常表示、JEV 結果が届いたら Lens 表現を重ねる非同期 UI
- MapLibre のデータ駆動スタイル（`feature-state` または属性更新）で実現できる
- 表示範囲の POI は数千件規模（東京駅周辺 z14 で約 4,000〜5,000 件）

## 未決事項
- `feature-state` で更新するか、GeoJSON ソースを差し替えるか（数千件なら差し替えでも足りる）
- Lens 切り替え時のトランジション
- 沈む側の透明度の下限（暗すぎたら弱める）

## 決定（2026-09-22、着手前の構成）
- フロントエンド: **Vite + TypeScript（フレームワークなし）**。MapLibre と COGP リーダーが主役で UI は小さいため
- 背景地図: **地理院地図 Vector と OSM（OpenFreeMap）を UI で切り替え可能、既定は地理院地図 Vector**。日本域では地理院の品質を活かし、日本以外や OSM 由来 POI との突き合わせが要るときは OpenFreeMap に切り替える（2026-09-22 修正）
- JEV 呼び出し（当面）: **Vite dev サーバーに `POST /api/evaluate-tags` を仮実装**し、`.env` のキーで Vercel AI Gateway を呼ぶ。本番 BFF（#4）と同じ API 形にして後で移す
- **Score は絶対基準（2 = 変化なし）を固定**。Lens ごとの正規化はしない（静か Lens で都心が沈むのは Lens の主張として受け入れる）。暗すぎれば沈む側の表現だけ弱める
- **表現の割り当て**: 点の大きさ = |Score−2|（浮く側は大きく、沈む側は小さく）/ 透明度 = 沈む側の Score（沈むほど薄く、浮く側は不透明）/ 色 = Choice v3 の確率分布を混色（主役・脇役・背景・妨げ・無関係の 5 色）/ 確信度 Noul は見え方に使わず POI 集約の重みのみ / Popup に名前・タグ一覧・各タグの Score / Choice / 確信度・集約結果
- **配色は Okabe-Ito 系**: 主役 = 朱 #D55E00 / 脇役 = 橙 #E69F00 / 背景 = 青緑 #009E73 / 妨げ = 青 #0072B2 / 無関係 = 灰 #999999。暖色 = Lens に沿う、寒色 = 反する。Score が浮沈を担うので色は浮く側 3 つの区別を主眼にする
- **混色は 5 色を Choice の確率で加重し OKLab で混ぜる**。無関係が灰なので判断が割れた POI は自然にくすむ。凡例は 5 色の純色を置き「中間色は判断が割れている」と説明
- Lens 適用前は全 POI を一律の小さな点（#13）

## 結論（2026-09-22、段階 8 の実装をもって）

決定は上の「決定（2026-09-22、着手前の構成）」がそのまま生きている。実装で足したのは
**JEV の欠測をどう見せるか**の 3 点（未評価と無関係を色で分ける / 届いたプリミティブだけ反映する /
失敗は手動で再試行）と、未決だった 3 つの決着（GeoJSON 差し替え・トランジションなし・透明度の下限 0.3）。

次に持ち越すもの。

- **冷えた Lens は上流の状態次第で 1〜3 分かかる。** キャッシュ（#6、段階 9）が効くまで
  「Lens を切り替えて見比べる」使い方が成立しない
- **細分タグ優先の規則（#7）は観光客 Lens を地図で見てから決める。** 数値上は
  分類タグの重みを半分にしても足りないことが分かっている
- **未評価の濃い灰は、z14 の 3 px では無関係の明るい灰と見分けづらい。** 拡大すれば分かるが、
  件数表示に頼っている面がある。凡例の説明か、未評価だけ形（縁の色）を変えるかは要検討

## 実装（2026-09-22、段階 8）

```
src/lens/colors.ts     Choice 5 色と OKLab 加重混色
src/lens/aggregate.ts  タグ評価 → POI 評価（#7）と、見え方（半径・透明度・色）への割り当て
src/lens/client.ts     BFF 呼び出し・NDJSON の読み取り・評価の保持・失敗の記録
src/main.ts            Lens の UI と地図への反映
```

### 未決事項の決着

- **`feature-state` ではなく GeoJSON を丸ごと差し替える。** 表示範囲は 5,845 件（z14）で、
  評価が届くたびの再集約と `setData` は体感できるほどの負荷にならない。`feature-state` だと
  背景地図を切り替えるたび（style ごと差し替わり層を入れ直す）に状態を張り直す必要があり、
  更新経路が 2 本になる
- **Lens 切り替えのトランジションは入れない。** 評価は NDJSON でバッチごとに届くので、
  地図は 1 回ではなく何度も塗り替わる。補間を掛けるとその途中経過が「動き続ける画面」になる
- **沈む側の透明度の下限は 0.3。** これ以上薄いと淡色の背景地図に埋もれ、「沈んでいる」ではなく
  「無い」に見える。浮く側は一律 0.9 とし、浮沈の強さは点の大きさに担わせる

### 大きさの基準

素の点（Lens 適用前）は z14 で半径 3 px。**Score 2（変化なし）をこの 3 px に合わせた**ので、
「Lens と無関係」と判断された POI は Lens を掛けても大きさが動かない。Score 0 で 1.5 px、
4 で 6 px。Lens は POI を増減させないという主題が、点の増減ではなく大小として出る。

### MapLibre の制約（実装時に踏んだ）

`['*', ['interpolate', ['linear'], ['zoom'], …], ['get', 'lensRadius']]` は
**`zoom` 式はトップレベルの `step` / `interpolate` の入力にしか置けない**という規則に触れ、
`addLayer` 時に例外になる（層が追加されず POI が 1 つも出ない）。
掛け算は各ストップの中に入れて `['interpolate', …, 10, ['*', 0.533, ['get', …]], …]` とする。

### JEV の障害を前提にした見せ方

JEV は公開直後で上流の一時障害が通常運用でも起こる（#4）。BFF が指数バックオフで 6 回
粘ってもなお落ちるバッチがあるので、**評価が全部揃うことを前提にしない**。決めたのは 3 つ。

1. **未評価と「無関係と判断された」を色で分ける。** 未評価は濃い灰 `#333333`（= 素の点）、
   無関係は明るい灰 `#999999`。同じ灰にすると、**評価が届いていないだけの POI を
   「Lens と無関係」と読ませてしまう**。#13 で「読めていないだけ」を「少ない」と
   読ませない方針を採ったのと同じ理由
2. **プリミティブが不揃いでも届いたものだけ反映する。** Score だけ届いた POI は
   大きさ・濃さが動いて色は灰のまま、Choice だけ届いた POI は色だけ付く。
   3 つ揃うまで待つと、1 バッチの失敗で多くのタグが落ちる
3. **失敗したバッチは自動で再送せず、画面に出して利用者に押させる。** 上流が不調なときは
   自動連打が効かないことが実測で分かっている（並列度を上げても完了時間は縮まなかった）。
   「失敗した N 件を再試行」ボタンを出し、押されたときだけ失敗したタグを送り直す

画面には **Lens 適用 / 一部のタグのみ / 色が未達 / 未評価** の件数を出す。
「地図が Lens をどこまで反映できているか」を数で見せておかないと、欠測が Lens の答えに見える。

## 実測（2026-09-22、段階 8 / 上流が不調な時間帯）

z14 の東京駅周辺（1280×800、5,845 件、評価対象タグ 623 種、冷えた Lens「子供が楽しめそう」）。

| | バッチ順 = プリミティブ優先 | バッチ順 = タグ優先（採用） |
| --- | --- | --- |
| リクエスト | 21 | 21 |
| 完了まで | 108.2 秒（失敗 6: server 6） | 199.9 秒（失敗 4: rate_limit 1 / server 3） |
| 12 秒時点 | — | 3 バッチ → 5,027 件に適用（うち 4,202 件はタグの評価が全部揃い） |
| 20 秒時点 | 14 バッチ → 適用 5,726 件。**ただし色はまだ全部灰** | — |
| 完了時 | 適用 5,726 件（一部のみ 157）/ 未評価 119 | 適用 5,772 件（一部のみ 81）/ 未評価 73 |

- **所要時間の差（108 秒 対 200 秒）は上流の状態の差**で、実装の差ではない。#4 のとおり
  所要時間は設計の前提にしない
- **効いたのは順序。** プリミティブ優先だと Choice が最後にまとまって届くので、
  20 秒経っても「大きさだけ動いて色は灰」の画面だった。タグ優先だと 12 秒で 4,202 件が完成する
- 失敗したバッチが残るぶん、完了時点でも未評価が 73 件残った。再試行ボタンで埋められる

### BFF に届かないとき（`page.route` で接続拒否を注入した実測）

z17・394 件・176 タグで、`POST /api/evaluate-tags` を接続拒否にした状態で Lens を適用。

- 「評価できていません・BFF に届かない（Failed to fetch）」と出て、地図は素の点のまま
  （適用 0 件 / 未評価 394 件）。**Lens 適用前の表示が壊れない**
- 再試行ボタンに「失敗した 528 件を再試行」（176 タグ × 3 プリミティブ）
- 接続を戻して押すと 6 バッチ 15〜24 秒で埋まり、384 件に Lens が載った。
  残った失敗のぶんだけボタンは減って残る（「失敗した 90 件を再試行」）
- Choice のバッチが 503 で落ちた回は「Lens 適用 384 件（色が未達 311 件）」と出た。
  **画面の黒い点の多さと数字が一致する**ので、「なぜ色が付かないのか」を読み手が追える
