# Semantic Cache の設計
labels: design, performance

## なぜ検討が必要か
同じ Lens・同じタグを何度も JEV に評価させないことが、コストと応答速度の両方を決める。

## 現在わかっていること
- キー候補: `Lens + 正規化タグ + JEV モデル版 + 評価スキーマ版`
- `key=value` 上位 1 万ペアで世界の出現 91% をカバー。**事前計算（Lens プリセットに対して全上位ペアを評価済みにしておく）が現実的な規模**
- Lens は自由入力なので、Lens 文字列の正規化（空白・句読点・同義表現）をどこまでやるかで命中率が変わる
- 最初はブラウザ内キャッシュ（IndexedDB）だけでも成立する



## Vercel AI Gateway の実測（2026-09-22、実験 01 全体）

| 項目 | 値 |
| --- | --- |
| リクエスト数 | 1.5K（成功 約 950、残りは 429 / 503 で再試行したもの） |
| 成功率 | **65.3%** |
| トークン | 約 10M（入力 約 9.5M） |
| 課金 | **$0.00**（`typesafe-ai/jev` の Cost 欄も $0） |
| Gateway 側 P50 Duration | 198 ms（クライアント実測は 40 問で約 550 ms） |
| 予算 | キー $5 / チーム $10 |

- Gateway 経由の JEV は現時点で **課金されていない**。コストの制約は金額ではなく **レート制限（成功率 65%）** にある
- 上流の混雑（429 "high demand"）と 503 が散発する。BFF には指数バックオフの再試行と、同時リクエスト数の制限が必須
- キャッシュの目的は金額よりも **レート制限の回避**。同じ Lens × タグの再評価を避けることが成功率と応答時間に直結する

## 未決事項
- 階層: ブラウザ → Workers Cache API / KV → JEV、の 3 層にするか
- Lens の正規化方針（完全一致のみ / 軽い正規化 / 同義 Lens の束ね）
- スキーマ版を上げたときの無効化
- プリセット Lens の事前計算を行うか、行うなら対象ペア数の閾値

## 結論（2026-09-22、初期形）
- **鍵**: `Lens 正規化文字列` + `タグ ID（key=value）` + `プリミティブ（noul / score / choice）` + `評価スキーマ版` + `JEV モデル版`。プリミティブ単位にするのは Score だけ問い直す・Choice の版だけ上げるを独立に行うため。評価スキーマ版は問い方（state の注意書き・criteria・Choice 選択肢）を変えたら上げる。JEV モデル版はレスポンスの `model`（`/v1/evaluate` なら返ることを実験 02 で確認。実験 01 の `/v4/ai/evaluation-model` では返らなかった）
- **Lens の正規化は軽く**: 前後空白除去・連続空白圧縮・全角英数記号の半角化・末尾句点除去。同義表現（子ども / 子供）は束ねない
- **保存はブラウザの IndexedDB のみで開始**。値はタグ単位の評価結果（Score・Choice 確率・確信度・モデル版・取得日時）。BFF（#4）移行時にサーバー側第 2 層（KV / Cache API）を足すかは命中率の実測で判断
- プリセット Lens の事前計算（上位 1 万ペア × プリセット）は自由入力に効かないため、後段の検討事項として残す

## 段階 8 で入れたぶん（2026-09-22）

段階 8 では **Lens ごとのメモリ内 Map** だけを置いた（`src/lens/client.ts`）。
地図を動かして表示範囲が変わっても、一度評価したタグは再評価しない。
ページを読み込み直すと消えるので、保存（IndexedDB）は段階 9 に残す。

鍵は結論どおり `Lens 正規化文字列 + タグ ID + プリミティブ`。評価スキーマ版と JEV モデル版は、
1 セッションの中では変わらないのでメモリ上の鍵には入れていない。IndexedDB に移すときに足す。

**キャッシュの効き目は当初の想定より大きい。** z14 の東京駅周辺で冷えた Lens は
623 タグ × 3 プリミティブ = 21 リクエストになり、上流が不調な時間帯には 2 分近くかかる。
キャッシュが無ければ Lens を試すたび・別の街に飛ぶたびにこれを繰り返すことになる。

## 実装（2026-09-22、段階 9 → `src/lens/store.ts`）

- 保存先は **IndexedDB**。`localStorage` は同期 API で 5 MB 前後の上限があり、
  1 Lens あたり 1,869 レコードには向かない
- **DB のバージョンに評価スキーマ版（`SCHEMA_VERSION`）をそのまま使う。** 問い方を変えたら
  この定数を上げる決まりなので、上げた時点で `onupgradeneeded` が走って古い評価を丸ごと捨てられる
  （未決事項の「スキーマ版を上げたときの無効化」）。移行はしない
- 鍵は `Lens 正規化文字列 \0 タグ ID \0 プリミティブ`。読み出しは `IDBKeyRange` で
  Lens 単位にまとめて取る（1 件ずつ get すると 1,779 回の往復になる）
- 開けない環境（プライベートウィンドウ等）では **キャッシュ無しで動く**。`EvalCache.open()` が null を返す
- 画面に「キャッシュを消す」ボタンを置いた。問い方を変えて試すときに手で捨てられるようにするため

### 鍵から JEV モデル版を外した（結論の修正）

上の結論では鍵に JEV モデル版を含めるとしていたが、`/v1/evaluate` が返す `model` は
**`typesafe-ai/jev` という版を含まない固定文字列**だった。これを鍵に入れても版の変化は
検出できないので、**鍵には使わず値に記録するだけ**にした。無効化は評価スキーマ版と手動削除で行う。

実験 02 で「`model` が返るからキャッシュ鍵に使える」と判断したが、返る中身を見れば
版の情報はない。**「返ること」と「版が分かること」は別だった。**

### 実測（2026-09-22、z14 東京駅周辺・5,845 件・評価対象タグ 623 種）

| | |
| --- | --- |
| 1 回目（キャッシュ空） | 21 バッチ / 147.9 秒（失敗 1） |
| 保存された評価 | 1,779 件（623 × 3 − 落ちた 1 バッチ 90） |
| 2 回目（再読み込み後） | **1,779 件を 8 ms で復元**。BFF へ行くのは前回落ちた 1 バッチだけ |
| 別の街（大阪 z14）へ移動 | 新しいタグのぶん 9 バッチだけ走る |
| 東京へ戻る | リクエスト 0 本、キャッシュから即復元 |

同じ Lens・同じ範囲なら **147.9 秒 → 8 ms**。「Lens を切り替えて見比べる」が成立するようになった。

再読み込みすると失敗の記録（手動再試行の対象）は消えるので、**前回落ちたタグは次に開いたときに
自動でもう一度投げられる**。手動再試行は「同じセッションで押し直す」話なので、これは意図どおり。
