# JEV BFF（`POST /api/evaluate-tags`）の選定
labels: design, infra, decision-needed

## なぜ検討が必要か
ブラウザから JEV API を直接呼ぶと API キーが露出する。TypeSafe 直 API は CORS がオリジン許可制でもある。
単なる Proxy ではなく、正規化・キャッシュ・スキーマ版管理を持つアプリ固有 API を置きたい。

## 現在わかっていること
- 候補: Cloudflare Workers / AWS Lambda / Vercel AI Gateway 直 / Cloudflare Workers + Vercel AI Gateway / JEV 直 Proxy
- 比較軸: 無料枠、個人実験コスト、実装量、運用の簡単さ、API キー管理、CORS、キャッシュ、将来の拡張性
- POI ホスティングを Cloudflare R2 にするなら（#5）、Workers が同一基盤でまとまる
- Cloudflare Workers 無料枠: 10 万リクエスト/日。KV / D1 / Cache API も無料枠あり
- Vercel AI Gateway は JEV への到達手段として動作確認済み（別プロジェクトの知見）。TypeSafe 直 API は Workers からなら CORS 非該当



## Vercel AI Gateway の実測（2026-09-22、実験 01 全体）

| 項目 | 値 |
| --- | --- |
| リクエスト数 | 1.5K（成功 約 950、残りは 429 / 503 で再試行したもの） |
| 成功率 | **65.3%** |
| トークン | 約 10M（入力 約 9.5M） |
| 課金 | **$0.00**（`typesafe-ai/jev` の Cost 欄も $0） |
| Gateway 側 P50 Duration | 198 ms（クライアント実測は 40 問で約 550 ms） |
| 予算 | キー $5 / チーム $10 |

- Gateway 経由の JEV は現時点で **課金されていない**。コストの制約は金額ではなく **レート制限（成功率 65%）** にある
- 上流の混雑（429 "high demand"）と 503 が散発する。BFF には指数バックオフの再試行と、同時リクエスト数の制限が必須
- BFF は再試行（429 / 503 / 529）と同時実行数の制御を持つこと。実験では最大 6 回・累計 2 分のバックオフで欠測 0 だった

## 未決事項
- JEV への到達経路: TypeSafe 直（Workers から）か Gateway 経由か。課金・キー管理・レイテンシで比較
- API 設計: リクエスト = `{ lens, tags[], schemaVersion }`、レスポンス = タグごとの評価 + キャッシュヒット情報、でよいか
- レート制限・悪用対策（公開デモにするなら必要）

## バッチサイズの決定（2026-09-22）

実験 01 の `BATCH = 40` に根拠はなかった（`run.ts` は「なぜ束ねるか」は書くが「なぜ 40 か」は書いていない）。
仕様を確認して **90 に上げる**。文言は現行のまま変えない。

### JEV 側の制限（docs.typesafe.ai）
- **質問数そのものに上限の記述はない**。効くのはトークン予算だけ
- **64k トークン / リクエスト**が `state` + 全質問の合計に対する予算
- 別枠の **32k トークン**は「`state` + 最も長い 1 問」に対する上限。1 問 337 トークンの本件には効かない
- 質問を増やしてもレイテンシはほとんど変わらない（`state` を一度取り込み全質問を並列評価するため）。
  公式 cookbook の実測では 13 問を 1 リクエストにまとめると 1 問ずつ 13 回より **12.2 倍安く 10 倍速い**。
  回答はバッチングで変わらず、run 間の標準偏差も一致した

### なぜ 90 か
- Vercel の Jev モデルページは context window を **32,000** と表示しており、TypeSafe 公式の 64k と食い違う。
  Vercel の別ガイドは 64k 側に一致する
- **90 はどちらが正しくても安全**。32k 説でも最も重い Choice が 94 問入る（1 問 337 トークン、`state` 300 トークン）。
  実測を待たずに 2.25 倍にできる
- プリミティブごとに分けない。Choice に合わせた共通値にする。分けても得られる差より設定の複雑さが勝る
- 64k が正しいと実測できたら Choice 189・Score 307・Noul 345 まで上げられる（後日）

z14 の冷えた Lens（623 タグ × 3 プリミティブ）のリクエスト数は **48 → 21**。

## 質問の定型部分について（2026-09-22、調査結果・未着手）

保存済みリクエストの実測で、**質問の 95〜98% が全問同じ定型文**で、変わるのはタグ名の約 10 文字だけと分かった。
`state` は 357 文字で入力の 2〜4% しかない。

**1 リクエスト内で指示や基準を共有する仕組みは仕様にない。**

- `instructions` は質問ごとに必須
- `questions` のキーはモデルに渡らないため、タグ名は `instructions` の中に書くしかない
- `state` は「評価する中身と補足事実」を置く場所で、判断基準は質問側という分担。基準を `state` に移す使い方は文書化されていない

一方、仕様が明示的に許す範囲で**質問を薄くする**余地は 54% ある。

| プリミティブ | 根拠 | 現行 | 削減後 | 削減率 |
| --- | --- | --- | --- | --- |
| Noul | `criteria` は任意なので落とせる | 221 | 94 | 57% |
| Score | レベルは短いラベルでよい（公式例も `["Calm", "Frustrated", "Very angry"]`） | 248 | 143 | 42% |
| Choice | 値に `null` を使える（"use null when an option needs no extra detail"） | 403 | 168 | 58% |

ただしこれは**基準の文言を消す**ことで、出力が変わりうる。実験 01 は Choice の文言を v1〜v3 と詰めた経緯があるので、
削るなら実験 01 の結果と突き合わせる別の実験が要る。**バッチサイズの決定とは切り離し、今回は触らない。**

## 実測で確定（2026-09-22、実験 02 → `experiments/02-jev-request-limits/`）

### 経路は `/v1/evaluate` にする
3 つとも 200 を返すが、返る中身が違う。

| 経路 | `model` | `confidence` | 文書化 |
| --- | --- | --- | --- |
| `/v4/ai/evaluation-model`（実験 01 の現行） | 返らない | 返らない | 見当たらない |
| `/v1/evaluate` | 返る | 返る | あり |
| `/typesafe/v1/systemone` | 返る | 返る | あり |

`/v1/evaluate` を採る。文書化されており `model` が返るので、#6 のキャッシュ鍵の
「Gateway 経由で返らなければ `unknown`」という但し書きを外せる。

### 予算は 64k（Vercel のモデルページの 32,000 は誤り）
110 問 34,861 トークンが 200。190 問 59,824 トークンも 200。230 問で `max_tokens_exceeded` の 400。
1 問あたり 315〜317 トークンで安定し、Choice の上限はおよそ 200 問。

### バッチサイズ 90 は維持。ただし理由が変わった
当初は「32k 説でも安全だから」90 にしたが、**実際の制約は予算ではなく成功率**だった。

| 問数 | 中央値 | 1 問あたり | 成功 |
| --- | --- | --- | --- |
| 45 | 725〜772 ms | 16〜17 ms | 6/6 |
| 90 | 879〜949 ms | 10 ms | 6/6 |
| 130 | 907〜1,009 ms | 7〜8 ms | 2/6 |
| 190 | 1,163 ms | 6 ms | 1/6 |

- レイテンシは質問数にほぼ比例しない（4.2 倍の質問で 1.5 倍の時間）。公式の主張どおり
- しかし **130 問以上で 503 が頻発**。全実行で 110 問以下は 9/9、130 問以上は 16 回中 4 回しか通らない
- **サイズが原因で、順序ではない。** 大→小の順で 190 問を最初に投げても 3 回とも落ちた
- 90 は 100% 通った最大サイズ。110 も通ったが 1 回きりで、リクエスト数 22% の差に見合う確証がない

z14 の冷えた Lens は 48 → 21 リクエスト。1 リクエスト約 0.9 秒で逐次 19 秒。
同時実行で縮めるが、**同時実行も 503 を誘発しうる**ので実装時に測り直す。

## 実装（2026-09-22、dev サーバーの仮 BFF）

`src/server/`（Vite 非依存）に置き、`vite.config.ts` から `/api/evaluate-tags` に繋ぐ。
本番の実行基盤が決まったらそのまま移せる。

- `jev.ts` — JEV 呼び出しの共通口。すべてここを通す
- `questions.ts` — state と質問の組み立て。文言は実験 01 と一字一句同じ（`SCHEMA_VERSION = 1`）
- `evaluate-tags.ts` — バッチ分割・同時実行・NDJSON の組み立て

### 応答は NDJSON
z14 の冷えた Lens は 21 バッチある。全部揃うまで待たせると数十秒動かない画面になるので、
終わったバッチから 1 行ずつ流す（README の「取得と評価を分離する」）。
失敗したバッチだけを個別に伝えられるのも、成功率が安定しない相手には効く。

`start` / `result` / `error` / `done` の 4 種。`done` に成功数・失敗数・種別ごとの回数を載せる。

### 一時障害を前提にした作り
JEV は公開直後でサービス側の不調が通常運用でも起こる。実測の失敗は**すべて 503**で
`429` は 1 件もなく、レート制限には当たっていない。503 の本文には Gateway の
`providerMetadata` が入り、上流 `typesafe-ai` が 503 を返したことが明示されている。

- 失敗を `rate_limit` / `overloaded` / `server` / `timeout` / `network` / `invalid` / `auth` に分類
- 再試行するのは一時障害のみ（`invalid` と `auth` は即座に返す）
- 指数バックオフ + ジッタ。`Retry-After` があれば優先
- 最大 6 回。使い切ったら呼び出し元に種別と本文を返す
- 全リクエストを `logs/jev.ndjson` に記録（日時・status・本文・`generationId`・経路・
  モデル・質問数・入力サイズ・試行回数・応答時間）

### 実測（2026-09-22、上流が回復した時間帯）
200 タグ × 3 プリミティブ = 9 バッチが **4.9 秒で全部成功**。最初の結果は 0.7 秒で届いた。
9 バッチ中 4 回 503 を踏んだが、最初の待ちを 300 ms にしてあるため再試行 1 回で通っている。

同じ日の障害中には 7 バッチを片付けるのに 30〜69 秒かかり、1 バッチあたり平均 3.6 回の試行を要した。
**上流の状態で 1 桁変わる**ので、所要時間を設計の前提にしない。

## 残っている改善案（未着手）

### 1. バッチを問数ではなく「1 リクエストの重さ」で切る → **採用**（実験 03 + 通し実測）

前提だった「境界は問数かどうか」を `experiments/03-batch-boundary/` で確かめた。
**問数を 130 に固定して中身だけ変えると成功率が動く**（41k で 0%、24k で 20%、20k で 30%）。
問数で並べると逆転があるので、問数は説明にならない。

そこで一度 29,000 トークンで切るようにして z14 の 623 タグを通しで流したところ、
**同じトークン量の 2 つが分かれた**。

| 1 リクエスト | 問数 | 入力トークン | 本文（文字数） | 成功 |
| --- | --- | --- | --- | --- |
| Noul | 190 | 14.4k | 25.0 KiB | 42%（5/12） |
| Choice | 91 | 28.9k | 34.4 KiB | 21%（8/38） |
| Score | 156 | 28.9k | 39.4 KiB | **3%（1/35）** |

- トークン量では説明できない（28.9k で揃えた 2 つが 21% 対 3%、Fisher の正確検定で p = 0.029）
- 問数でも説明できない（問数が最多の Noul 190 問が最も通る）
- **本文の大きさで並べると単調に下がる**

最終的に予算を **Choice 90 問の本文（34.0 KiB）** に置いた。実験 02 で全実行 100% 通った
唯一のサイズで、不調な時間帯でも 21% と他より明確に良かった。

| プリミティブ | バッチサイズ | 本文 | 623 タグでの本数 |
| --- | --- | --- | --- |
| Choice | 90〜91 問 | 33.7〜34.0 KiB | 7 |
| Score | 134〜136 問 | 33.8〜34.0 KiB | 5 |
| Noul | 190 問（問数上限） | 24.8〜25.0 KiB | 4 |

**21 本 → 16 本。** 問数の上限 190 も併せて置いた（実験 02 / 03 / 通し実測で通った実績のある
最大値。文字数だけ見れば Noul は 259 問積めるが、そこは未検証）。

プリミティブごとにバッチサイズが違うので、ジョブは分割後に「先頭のタグを扱うもの」から
順に並べ替える。出現数の多いタグから 3 プリミティブ揃って届く性質は保つ。

**残る前提**: 実験 03 も通し実測も上流が不調な時間帯のもので、「34.0 KiB が通る」絶対値は
測れていない（Choice 90 問相当が 21% しか通らない状況だった）。健全な時間帯に測り直す。

**副産物**: `logs/jev.ndjson` の `requestBytes` は `JSON.stringify(body).length`、つまり
文字数を入れていた。日本語主体の本文ではバイト数の半分以下になり実測を読み違えるので、
`requestChars` に改名した。

### 2. 質問の定型部分を削る（54% 減）→ **Noul だけ削れる**（実験 04 で決着）

`experiments/04-question-slimming/` で、現行版と削減版を同じ実行の中で隣り合わせに投げて比べた。

| プリミティブ | 入力の削減（実測） | 判断の一致 | 判定 |
| --- | --- | --- | --- |
| Noul | 51%（155 → 76 トークン） | 集約後の 3 値で 97.5〜98.9% | **削る** |
| Score | 44%（185 → 104） | 3 値で 84.4%（kids） | 削らない |
| Choice | 64%（318 → 116） | 最尤で 85.6%、分布の L1 距離 0.25 | 削らない |

- Score と Choice は**地図に出る判断が 14〜16% 変わる**。実験 01 で Choice の文言を
  v1〜v3 と詰めた経緯とも整合する（基準の書き方は結果に効く）
- Noul は確信度そのものが 0.09〜0.11 系統的に高く出るが、使うのは POI 内の相対値だけで、
  #7 の集約式に通すと差は中央値 0.011（3 値の一致 97.5〜98.9%）
- ただし **Noul だけ削ってもリクエスト本数は変わらない**（いまは問数で切っているため）。
  効果が出るのは改善案 1 と組み合わせたときなので、両方そろってから入れる

### 3. 上流が健全なときにサイズと並列度を測り直す（まだ）
実験 02 の結論のうち、予算 64k 以外はサービス障害と交絡している。
**実験 03 を 2 回走らせたが、どちらも対照が落ちる時間帯だった**（1 回目 0/4、2 回目 1/6）。
条件間の相対比較はできたが、絶対値（健全時にどのサイズまで通るか）と並列度は測れていない。

## 段階 8 でわかったこと（2026-09-22）

### 429 を初めて観測した

実験 01・02 と BFF の実装時は**失敗がすべて 503** で、`429` は 1 件も出ていなかった。
段階 8 で z14 の冷えた Lens（623 タグ = 21 バッチ）を通しで流したところ、
**503 に混ざって 429 が出た**。`Retry-After` は 50 秒前後で、指数バックオフの待ち（最大 6 秒）より長い。

- `Retry-After` を優先する実装になっているので、待ちは 50 秒に伸びて通った
- つまりレート制限は「当たらない」のではなく、**まとまった本数を短時間に投げると当たる**。
  実験 01・02 は 1 回あたりの本数が少なく、当たる前に終わっていた
- 同時実行数（現在 2）を上げる話は、503 だけでなく 429 も見て決める必要がある

### バッチの順序をプリミティブ優先からタグ優先に変えた

当初は `for プリミティブ { for タグのバッチ }` の順で並べていた。これだと Noul と Score が
全部届いたあとに Choice が届くので、**大きさだけ動いて色は灰のまま**という中途半端な画面が
長く続く（実測で 20 秒ほど）。

`for タグのバッチ { for プリミティブ }` に変えると、先頭のバッチから 3 プリミティブが揃って届く。
クライアントはタグを出現数の多い順に送るので、**多くの POI に効くタグから順に完成した見え方**になる。
リクエストの総数は変わらない。

- 変更後の実測: 12 秒 = 3 バッチ（先頭 90 タグ × 3 プリミティブ）で 5,845 件中 5,027 件に
  Lens が載り、うち 4,202 件は持っているタグすべての評価が揃っていた

## 結論（2026-09-22、一部）
- JEV への到達経路は **Vercel AI Gateway** に決定（$5 無料枠。実験と BFF で経路を揃える）。BFF の実行基盤（Workers か否か）は未決
- バッチサイズは **90**、経路は **`/v1/evaluate`**（上記「実測で確定」）
