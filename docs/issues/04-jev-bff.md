# JEV BFF（`POST /api/evaluate-tags`）の選定
labels: design, infra, decision-needed

## なぜ検討が必要か
ブラウザから JEV API を直接呼ぶと API キーが露出する。TypeSafe 直 API は CORS がオリジン許可制でもある。
単なる Proxy ではなく、正規化・キャッシュ・スキーマ版管理を持つアプリ固有 API を置きたい。

## 現在わかっていること
- 候補: Cloudflare Workers / AWS Lambda / Vercel AI Gateway 直 / Cloudflare Workers + Vercel AI Gateway / JEV 直 Proxy
- 比較軸: 無料枠、個人実験コスト、実装量、運用の簡単さ、API キー管理、CORS、キャッシュ、将来の拡張性
- POI ホスティングを Cloudflare R2 にするなら（#5）、Workers が同一基盤でまとまる
- Cloudflare Workers 無料枠: 10 万リクエスト/日。KV / D1 / Cache API も無料枠あり
- Vercel AI Gateway は JEV への到達手段として動作確認済み（別プロジェクトの知見）。TypeSafe 直 API は Workers からなら CORS 非該当



## Vercel AI Gateway の実測（2026-09-22、実験 01 全体）

| 項目 | 値 |
| --- | --- |
| リクエスト数 | 1.5K（成功 約 950、残りは 429 / 503 で再試行したもの） |
| 成功率 | **65.3%** |
| トークン | 約 10M（入力 約 9.5M） |
| 課金 | **$0.00**（`typesafe-ai/jev` の Cost 欄も $0） |
| Gateway 側 P50 Duration | 198 ms（クライアント実測は 40 問で約 550 ms） |
| 予算 | キー $5 / チーム $10 |

- Gateway 経由の JEV は現時点で **課金されていない**。コストの制約は金額ではなく **レート制限（成功率 65%）** にある
- 上流の混雑（429 "high demand"）と 503 が散発する。BFF には指数バックオフの再試行と、同時リクエスト数の制限が必須
- BFF は再試行（429 / 503 / 529）と同時実行数の制御を持つこと。実験では最大 6 回・累計 2 分のバックオフで欠測 0 だった

## 未決事項
- JEV への到達経路: TypeSafe 直（Workers から）か Gateway 経由か。課金・キー管理・レイテンシで比較
- API 設計: リクエスト = `{ lens, tags[], schemaVersion }`、レスポンス = タグごとの評価 + キャッシュヒット情報、でよいか
- レート制限・悪用対策（公開デモにするなら必要）

## バッチサイズの決定（2026-09-22）

実験 01 の `BATCH = 40` に根拠はなかった（`run.ts` は「なぜ束ねるか」は書くが「なぜ 40 か」は書いていない）。
仕様を確認して **90 に上げる**。文言は現行のまま変えない。

### JEV 側の制限（docs.typesafe.ai）
- **質問数そのものに上限の記述はない**。効くのはトークン予算だけ
- **64k トークン / リクエスト**が `state` + 全質問の合計に対する予算
- 別枠の **32k トークン**は「`state` + 最も長い 1 問」に対する上限。1 問 337 トークンの本件には効かない
- 質問を増やしてもレイテンシはほとんど変わらない（`state` を一度取り込み全質問を並列評価するため）。
  公式 cookbook の実測では 13 問を 1 リクエストにまとめると 1 問ずつ 13 回より **12.2 倍安く 10 倍速い**。
  回答はバッチングで変わらず、run 間の標準偏差も一致した

### なぜ 90 か
- Vercel の Jev モデルページは context window を **32,000** と表示しており、TypeSafe 公式の 64k と食い違う。
  Vercel の別ガイドは 64k 側に一致する
- **90 はどちらが正しくても安全**。32k 説でも最も重い Choice が 94 問入る（1 問 337 トークン、`state` 300 トークン）。
  実測を待たずに 2.25 倍にできる
- プリミティブごとに分けない。Choice に合わせた共通値にする。分けても得られる差より設定の複雑さが勝る
- 64k が正しいと実測できたら Choice 189・Score 307・Noul 345 まで上げられる（後日）

z14 の冷えた Lens（623 タグ × 3 プリミティブ）のリクエスト数は **48 → 21**。

## 質問の定型部分について（2026-09-22、調査結果・未着手）

保存済みリクエストの実測で、**質問の 95〜98% が全問同じ定型文**で、変わるのはタグ名の約 10 文字だけと分かった。
`state` は 357 文字で入力の 2〜4% しかない。

**1 リクエスト内で指示や基準を共有する仕組みは仕様にない。**

- `instructions` は質問ごとに必須
- `questions` のキーはモデルに渡らないため、タグ名は `instructions` の中に書くしかない
- `state` は「評価する中身と補足事実」を置く場所で、判断基準は質問側という分担。基準を `state` に移す使い方は文書化されていない

一方、仕様が明示的に許す範囲で**質問を薄くする**余地は 54% ある。

| プリミティブ | 根拠 | 現行 | 削減後 | 削減率 |
| --- | --- | --- | --- | --- |
| Noul | `criteria` は任意なので落とせる | 221 | 94 | 57% |
| Score | レベルは短いラベルでよい（公式例も `["Calm", "Frustrated", "Very angry"]`） | 248 | 143 | 42% |
| Choice | 値に `null` を使える（"use null when an option needs no extra detail"） | 403 | 168 | 58% |

ただしこれは**基準の文言を消す**ことで、出力が変わりうる。実験 01 は Choice の文言を v1〜v3 と詰めた経緯があるので、
削るなら実験 01 の結果と突き合わせる別の実験が要る。**バッチサイズの決定とは切り離し、今回は触らない。**

## 未確認（BFF 実装前に潰す）

  文書化されているのは `/v1/evaluate`（`model` 必須、Noul が `type: "boolean"`）と
  `/typesafe/v1/systemone`（本家と同じ形）の 2 つ。実験は 1.5K リクエストを通しているので動いてはいる
- リクエスト全体の予算が 64k か 32k か

## 結論（2026-09-22、一部）
- JEV への到達経路は **Vercel AI Gateway** に決定（$5 無料枠。実験と BFF で経路を揃える）。BFF の実行基盤（Workers か否か）は未決
- バッチサイズは **90**（上記「バッチサイズの決定」）
