# 実験 05: COGP の読み取りは何にバイトを使っているか

#9 の結論に「COGP の 0.9〜1.5 秒は転送量の 9 割が `tags` 列（#13）。Lens に必要なのは
許可リストを通ったタグだけなので、**読む列を絞れば縮む見込みがある**」と書いた。
この「9 割」も「絞れば縮む」も測っていない。#5（ホスティング）でデータを作り直すかどうかが
この見立てに乗っているので、先に実測する。

```bash
uv run experiments/05-transfer-size/columns.py            # メタデータ上のカラム別サイズ
node --experimental-transform-types experiments/05-transfer-size/read.ts [--zoom 14] [--no-coalesce]
node --experimental-transform-types experiments/05-transfer-size/granularity.ts
node --experimental-transform-types experiments/05-transfer-size/pages.ts
```

## 設計

- **ブラウザと同じ経路で測る。** ローカルファイルを AsyncBuffer にして
  `coalescing → rangeCache` の順で同じラッパを被せ、**一番内側（ネットワークが見る層）で
  バイト数を数える**。外で数えるとキャッシュ命中と Range 結合の水増しが混ざる
- **dev サーバーは使わない。** 知りたいのは「読むバイト数」で、HTTP を挟むと
  ネットワーク条件が混ざる。src も触らないので計測中に再起動が起きない
- 測るのは 3 つ。列の組み合わせ（read.ts）、範囲の広さ（granularity.ts）、
  ページと辞書の内訳（pages.ts）
- 視点は `main.ts` の `INITIAL_VIEW`（東京駅周辺）。段階 9 までの実測がすべてこの地点

## 結果（2026-09-22）

### 1. 列を絞ると縮む。ただし縮むのは `id` の分だけ

z14 / 1280×800 / L13、5,845 件。

| 読む列 | 読み取り | Range | 現行比 |
| --- | --- | --- | --- |
| 現行（全列） | 13.6 MiB | 154 | 100% |
| `id` + `geometry` + `tags` | 13.6 MiB | 154 | 100% |
| `geometry` + `tags`（id を落とす） | 10.0 MiB | 141 | **73.5%** |
| `id` + `geometry`（tags を落とす） | 5.6 MiB | 116 | 41.1% |
| `geometry` のみ | 2.0 MiB | 96 | 14.9% |
| `bbox` のみ（件数カウント経路） | 1.4 MiB | 79 | 10.5% |

`bbox` は絞り込みに要るのでリーダーが常に足す。**Lens は `tags` を落とせない**ので、
クライアント側で選べるのは実質「`id` を落とすか」だけで、効果は **26%**。

「転送量の 9 割が tags」は誇張で、実測は **59%**（13.6 − 5.6 = 8.0 MiB）。

### 2. ズームにも範囲の広さにもほとんど依存しない

| 視点 | 読み取り | 件数 | 1 件あたり |
| --- | --- | --- | --- |
| z12 | 13.1 MiB | 19,744 | 0.7 KiB |
| z14 | 13.6 MiB | 5,845 | 2.4 KiB |
| z16 | 14.3 MiB | 711 | 20.6 KiB |

レベルを L13 に固定して bbox だけ縮めても同じ。**面積を 1/1000 にしても 12% しか減らない。**

| 辺 | 面積比 | 読み取り | 件数 |
| --- | --- | --- | --- |
| 1x | 1 | 13.6 MiB | 5,845 |
| 0.25x | 1/16 | 12.2 MiB | 538 |
| 0.0625x | 1/256 | 12.2 MiB | 40 |
| 0.03125x | 1/1024 | 12.0 MiB | 5 |

### 3. 正体は辞書ページ

読む量の内訳（z14、候補 row group 14 本）。

| 内訳 | バイト数 | |
| --- | --- | --- |
| PageIndex が選んだデータページ | 3.6 MiB | 29% |
| **辞書ページ**（`tags.value` 5.79 + `id` 3.36 + `tags.key` 0.12） | **9.3 MiB** | **71%** |
| 合計 | 12.9 MiB | （実測 13.0 MiB と一致） |

- **ページ単位の絞り込みは効いている。** 候補 row group の 792,199 行のうち PageIndex が
  残すのは 44,967 行（5.7%）で、メタデータ上のカラム合計 58.2 MiB が 3.6 MiB まで落ちている
- 辞書ページは OffsetIndex に載らないが、**その列を読むなら row group ごとに必ず 1 つ読む**。
  1 件しか返らなくても 9.3 MiB 掛かるのはこれ
- `id`（int64・ほぼ一意）にも辞書が付いていて 3.36 MiB。ほぼ純粋な無駄で、
  実測の「id を落とすと 3.6 MiB 減る」はこの辞書がそのまま消えた分
- 1 ページは約 2,200 行 / 38 KiB（`tags.value`）。ページが粗いせいでも、
  ページの中身が空間的に散らばっているせいでもない

### 4. Range 結合は妥当な設定

`--no-coalesce` と比べると、結合は **+0.6 MiB（4.6%）で Range を 205 → 154 回に減らす**。
ここを触っても得はない。

## 結論

- **#9 の「読む列を絞れば縮む」は、`id` を落とす 26% 分だけ正しい。** `tags` は Lens の
  入力そのものなので落とせず、それ以外に絞る余地はない
- **残りは表示件数と無関係な固定費（辞書 9.3 MiB）で、クライアント側では削れない。**
  z16 で 711 件のために 14.3 MiB 読むのも、狭い範囲で 1 件あたりのコストが悪化するのも、
  すべてこれで説明がつく
- したがって #9 の「未着手」は **列の絞り込み（小）** と **データ側の作り直し（大）** に分かれる。
  後者（#5）で効くのは次の 3 つで、どれも辞書を小さくする方向:
  1. **日本域に切り出す** — 辞書が世界中の値ではなく日本のタグ値だけになる
  2. **row group を小さくする** — 1 本あたりの辞書が小さくなる（候補本数は増える）
  3. **`id` を落とす / `id` の辞書を切る** — それだけで 3.4 MiB
- `id` はいま画面で使っていない（`properties.id` を読む箇所がない）。落とせば 26% 減るが、
  OSM への参照や #11 の第 2 段評価で要るかもしれない。**#5 で独自スキーマを作るなら
  そこで決める**話で、リーダー側の列指定だけで先に入れる価値は薄い
