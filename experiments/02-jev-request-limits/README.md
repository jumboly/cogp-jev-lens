# 実験 02: JEV のリクエスト上限・到達経路・バッチサイズ

実験 01 の `BATCH = 40` に根拠がなく（`run.ts` は「なぜ束ねるか」は書くが「なぜ 40 か」は書いていない）、
BFF（#4）を書く前に実測で決める。あわせて、実験 01 が使っている経路が公式ドキュメントに
見当たらない件も潰す。

```bash
node --env-file=.env experiments/02-jev-request-limits/probe.ts              # 経路と予算
node --env-file=.env experiments/02-jev-request-limits/latency.ts            # バッチ別レイテンシ（小→大）
node --env-file=.env experiments/02-jev-request-limits/latency.ts --reverse  # 同（大→小、順序の交絡を切る）
```

計測はすべて Choice v3（3 プリミティブで最も重い、1 問 約 316 トークン）で行う。
文言は実験 01 と同一にして、01 の結果と比較できる状態を保つ。

## 1. 到達経路

3 つとも HTTP 200 を返すが、**返る中身が違う**。

| 経路 | `model` | `confidence` | 文書化 |
| --- | --- | --- | --- |
| `/v4/ai/evaluation-model`（実験 01 の現行） | 返らない | 返らない | 見当たらない |
| `/v1/evaluate`（Gateway ネイティブ） | 返る | 返る | あり |
| `/typesafe/v1/systemone`（互換） | 返る | 返る | あり |

**決定: `/v1/evaluate` を使う。** 文書化されており、`model` が返る。
Issue 6 のキャッシュ鍵は JEV モデル版に `model` を使うので、「Gateway 経由で返らなければ `unknown`」
という但し書きを外せる。`confidence`（Choice / Score）も返る。

## 2. リクエスト予算は 64k

| 問数 | 送信 | 結果 | 入力トークン |
| --- | --- | --- | --- |
| 100 | 82 KiB | 200 | 31,737 |
| 110 | 90 KiB | 200 | 34,861 |
| 190 | 154 KiB | 200 | 59,824 |
| 230 | 187 KiB | **400** | `max_tokens_exceeded` |

**Vercel の Jev モデルページが表示する context window 32,000 は誤り。** 110 問 34,861 トークンが通る。
TypeSafe 公式の「64k がリクエスト全体の予算」が正しい。1 問あたりは 315〜317 トークンで安定し、
Choice の上限はおよそ 200 問。

## 3. レイテンシは平坦、しかし成功率はサイズで崩れる

各サイズ 3 回ずつ。503 / 429 / 529 は最大 7 回の指数バックオフ（累計 2 分強）で待ち、
待ち時間は計測から除く。「断念」はそれでも通らなかった回。

| 問数 | 入力tok | 中央値（小→大） | 中央値（大→小） | 1 問あたり | 成功（両方向 計） |
| --- | --- | --- | --- | --- | --- |
| 45 | 14,626 | 772 ms | 725 ms | 16〜17 ms | **6/6** |
| 90 | 28,696 | 879 ms | 949 ms | 10 ms | **6/6** |
| 130 | 41,133 | 907 ms | 1,009 ms | 7〜8 ms | 2/6 |
| 190 | 59,824 | 1,163 ms | 通らず | 6 ms | 1/6 |

- **レイテンシは質問数に比例しない。** 4.2 倍の質問で 1.5 倍の時間。公式ドキュメントの
  「質問を足しても応答時間はほとんど変わらない」は成り立つ。1 問あたりは 17 ms → 6 ms に下がる
- **ただし 130 問以上で 503 が頻発する。** 探りを含めた全実行で、**110 問以下は 9/9 成功、
  130 問以上は 16 回中 4 回**しか通らない
- **原因はサイズであって順序ではない。** 「後半ほど混む」交絡を疑って大→小の順でも測ったが、
  190 問を**最初に**投げても 3 回とも落ちた。上流が大きいリクエストを混雑時に受け付けない挙動に見える

## 決定: バッチサイズ 90

- 全実測で 100% 通った最大のサイズ。110 も通ったが 1 回きりで、90 との差（リクエスト数で 22%）に
  見合うだけの確証がない
- プリミティブごとに分けない。最も重い Choice に合わせた共通値にする
- 予算 64k から見れば 190 まで積めるが、**予算ではなく成功率が制約**だった。
  レイテンシが平坦なので「積めるだけ積む」が有利に見えたが、実測は逆を示した
- ただしこの成功率は上流が不調な時間帯の測定である（下記 5）。健全時に測り直す余地がある

z14 の冷えた Lens（623 タグ × 3 プリミティブ）は **48 → 21 リクエスト**。
1 リクエスト約 0.9 秒なので逐次で約 19 秒。BFF では同時実行数を上げて縮めるが、
同時実行も 503 を誘発しうるので実装時に測り直す。

## 4. 並列度とスループット（2026-09-22、上流が不調な時間帯）

```bash
node --env-file=.env experiments/02-jev-request-limits/concurrency.ts   # 再試行なしの受け入れ率
node --env-file=.env experiments/02-jev-request-limits/throughput.ts    # 再試行込みで 7 バッチを片付ける時間
```

再試行なしの受け入れ率（バッチ 90、各 2 回）。

| 並列 | 成功 |
| --- | --- |
| 1 | 1/2 |
| 2 | 2/4 |
| 4 | 1/8 |
| 8 | 3/16 |

**並列度 1 でも半分落ちた。** 並列度の差はこのノイズに埋もれる。
再試行込みで 7 バッチ（630 タグ）を片付ける時間も、並列 1 で 30〜69 秒・1 バッチあたり平均 3.6 回の試行、
並列 2 で 30〜62 秒・4.4 回と、並列度を上げても縮まなかった。

## 5. 失敗はすべてサービス側だった（重要）

**全実行を通じて失敗は 503 のみで、`429` は 1 件も出ていない。**
つまりレート制限には当たっておらず、上流の一時障害である。503 の本文には Gateway の
`providerMetadata` が入り、上流 `typesafe-ai` が 503 を返したことが明示される。
追跡用の `generationId` も付く。

```json
{"error":{"type":"service_unavailable_error","param":{"statusCode":503}},
 "providerMetadata":{"gateway":{"routing":{"resolvedProvider":"typesafe-ai",
 "modelAttempts":[{"success":false,"providerAttempts":[{"statusCode":503}]}]},
 "generationId":"gen_01M33G1AWN783H5JCH7QF92NM2"}}}
```

JEV は公開直後で利用が急増しており、同日朝まで公式に intermittent downtime と
system instability が記録されていた。

### この実験の結論の読み方
- **「予算 64k」「230 問で `max_tokens_exceeded`」は確実。** 明示的な 400 が返るので障害とは無関係
- **「130 問以上で 503 が頻発」はサイズとの相関が見えるが、障害中の測定である。**
  大→小の順でも 190 問が最初から 3 回落ちたので順序の交絡ではないが、
  **上流が健全なときに測り直す価値がある**
- **並列度の結論は保留。** 障害中の並列度は一般化できない
- 後に上流が回復した時間帯では、並列 2 で 9 バッチが 4.9 秒で全部成功している（#4 の BFF 実測）。
  **上流の状態で 1 桁変わるので、所要時間を設計の前提にしない**
